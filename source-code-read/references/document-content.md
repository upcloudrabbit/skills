# Source Code Read 文档内容标准

本文档定义 `/source-code-read` 生成和整理文档时各章节必须包含的编写内容规范。
包含通用写作要求、每类文档各章节的内容细节要求和章节质量门禁。

章节结构（标题层级与顺序）见 [document-sections.md](document-sections.md)。

## 通用写作要求

- 所有判断必须能追溯到源码位置；没有源码证据时标注"未在当前分析范围内确认"。
- 每个章节先给结论，再给源码依据和关键细节；不要只罗列文件名或函数名。
- 代码引用使用工程内相对路径；工程外使用绝对路径，并在"代码引用索引"集中列出。
- 关键实现必须包含三维评估：好处、替代方案、风险。
- 涉及流程、状态、依赖或调用链时优先使用 Mermaid，并按 `restrictions.md` 的画图规范校验。
- 如果某章节确实不适用于当前模块或场景，保留章节标题并写明"不适用原因"，不要删除章节。

## 工程目录文档内容规范

### 技术栈与项目概述
- 用一段话说明当前应用的核心业务功能（做什么）。
- 列出使用的核心技术和主要编程语言（技术栈）。
- 包含项目名称、构建方式、项目规模、许可证、分析范围。
- 简短、精炼，约 100-200 字。

### 重点关注
- 列出最重要的阅读入口、核心模块或关键场景，并说明原因。

### 阅读路线
- 按新手、维护者、排障者、扩展开发者给出阅读顺序。

### 文档清单
- 列出所有生成的文档链接，按文档类型分组：工程概览、编译运行流程、模块文档、核心源码阅读、场景分析。
- 每个模块/核心分析/场景分析占一行，链接到对应 .md 文件。

### 模块功能摘要
- 表格列出模块、主要功能、核心入口、关键文档链接。

### 架构总览
- Mermaid graph，图后解释层次、依赖方向和关键耦合。

### 关键场景索引
- 列出 `byCase` 生成的场景文档、涉及模块和入口。

### 文档维护记录
- 记录本次新增/更新/归档的文档摘要。
- 每次文档有变动时追加记录。

## 工程概览文档内容规范

### 工程目录结构
- 首先用一段话总体介绍当前工程源码的目录结构组织方式（如分层的、模块化的、按功能划分的等）。
- 整体上描述各个一级目录的用途划分。

### 目录结构图
- 必须使用 Mermaid graph 绘制目录树，每级节点都要有简要说明。
- 根节点加入 `click` 链接到 `../工程目录.md`。
- 图后不需要额外步骤说明表，但节点标签本身须包含职责简述。

### 目录说明
- 针对目录图中每一级目录（从根目录到最内层源码目录），用一段话描述：
  - 当前目录下存放什么文件
  - 这些文件具体是干什么的
  - 如果某个子目录有对应模块文档，添加 `👉 详见 [{模块名}]({模块名}.md)` 链接

## 编译运行流程文档内容规范

### 技术栈与依赖
- 列出工程使用的编程语言、框架、中间件、数据库、第三方库。
- 用表格列出主要依赖及其版本和用途。
- 运行和编译的关键命令需要列出。

### 编译流程
- 包含编译环境准备和详细编译步骤，每步说明做什么以及对应的命令。
- 说明编译产物的输出位置和用途。

### 运行流程
- 包含本地运行方式和 Docker 运行方式（如果有）。
- 说明运行所需的配置、环境变量和启动参数。

### 测试流程
- 如果有测试用例模块，必须包含单元测试、集成测试的编译和运行流程。
- 说明测试框架、测试目录结构、运行命令。
- 如果工程没有测试用例模块，保留"测试流程"标题并注明"不适用"。

## 模块文档内容规范

### 重点关注

- 列出最值得阅读的章节或源码入口。
- 每项说明"为什么重要"，例如主链路、复杂分支、易错边界、扩展入口。

### 1. 模块定位与职责边界

- 说明模块解决什么问题、在项目中的上游/下游位置。
- 明确模块负责什么、不负责什么，避免把相邻模块职责混入。
- 给出主要输入、输出、状态变化和副作用。

### 2. 架构关系与依赖

- 说明模块内部子组件、外部依赖、反向依赖和关键数据流。
- 必须包含架构/依赖 Mermaid 图；图后附说明表，解释每个节点和依赖方向。
- 标注强依赖、可替换依赖、跨层调用和潜在耦合点。

### 3. 入口与调用方式

- 列出用户入口、API 入口、命令入口、事件入口、框架回调或定时任务入口。
- 每个入口说明触发条件、关键参数、返回值、权限/上下文要求。
- 指向入口源码位置，并说明入口之后进入哪些核心流程。

### 4. 核心概念与领域模型

- 每个概念必须包含：定义、作用、生命周期、相关类型/函数、代码示例或使用场景。
- 说明概念之间的关系，例如聚合、引用、状态拥有者、转换关系。
- 对关键模型给出"好处 / 替代方案 / 风险"三维评估。

### 5. 关键流程

- 至少覆盖主成功路径、一个重要失败路径、一个边界或异步路径。
- 每个流程必须包含 Mermaid flowchart 或 sequenceDiagram，首行插入 `{_mermaidThemeInit}`。
- 图后必须附步骤说明段落，按阶段分组并用 "序号范围" 开头（如"1-2 xxx"），一段话描述该阶段整体做了什么、关键判断和失败如何处理。

### 6. 核心实现细节

- 按核心类/函数/子系统拆分小节，解释实现为什么这样组织。
- 对关键代码给出逐段解读：输入、处理逻辑、输出、副作用、隐藏假设。
- 明确算法、缓存、状态机、资源管理、框架扩展点或反射/注解等非显而易见机制。
- 每个关键实现点包含三维评估：好处、替代方案、风险。

### 7. 数据结构、配置与外部协议

- 列出核心数据结构、配置项、环境变量、外部接口、消息格式或持久化结构。
- 说明字段含义、默认值、约束、兼容性要求和错误配置的后果。
- 如果模块没有外部协议或配置，说明它依赖哪些内部结构作为替代。

### 8. 异常、边界与降级处理

- 覆盖参数非法、依赖失败、空数据、超时、权限不足、重复调用、资源不可用等边界。
- 说明异常如何传播、捕获、转换、记录和恢复。
- 标注当前实现未覆盖的风险点，但必须基于源码证据。

### 9. 并发、生命周期与性能

- 说明对象/连接/线程/协程/订阅/缓存等资源的创建、复用和释放。
- 分析并发安全、顺序保证、幂等性、重试、背压或锁竞争。
- 标出性能关键路径、可能的瓶颈、复杂度或 I/O 热点。

### 10. 扩展点、测试点与维护建议

- 列出可扩展接口、策略点、插件点、配置扩展方式或新增功能的推荐入口。
- 给出建议测试点：主路径、失败路径、边界条件、回归风险。
- 提出维护建议时必须说明目标位置、问题、建议动作和收益/风险。

### 11. 文件职责表

使用表格列出模块关键文件：

| 文件 | 职责 | 关键类/函数 | 被谁调用 | 备注 |
|------|------|-------------|----------|------|

- 文件数量按模块规模选择，通常 5-20 个；不要用完整目录树替代职责分析。
- 每行必须说明该文件在模块链路中的角色。

### 12. 代码引用索引

集中列出本文引用过的源码位置：

| 引用 | 说明 |
|------|------|
| `src/example/File.ts:10` | 入口函数 |

- 引用必须服务于正文分析；不要收集没有在正文解释过的路径。

## 核心源码阅读文档内容规范

### 阅读向导
- 说明本分析面向什么类型的读者（新接手开发者、排障者、代码审查者等）。
- 给出阅读前建议先了解的模块文档或其他依赖文档链接。

### 1. 分析范围与目标
- 明确本分析涵盖的源码范围（文件、类、函数），不涵盖什么。
- 说明分析目标：理解核心算法、排查潜在缺陷、评估可维护性等。

### 2. 核心类/函数全景
- 用表格列出本分析涉及的核心类/函数，包括名称、职责、关键方法/属性、代码位置。

### 3. 关键数据结构
- 列出核心数据结构、接口、枚举、配置定义。
- 说明字段含义、生命周期、使用方式。
- 重点分析复杂数据结构的设计理由（如为什么选择 Map 而非 List）。

### 4. 主线流程逐行解读
- 从入口函数开始，按执行顺序逐段（逐函数）解读源码。
- 每段说明：做什么、为什么这样做、输入输出、状态变化。
- 必须引用具体源码行号。
- 包含 Mermaid flowchart 展示整体流程，首行 `{_mermaidThemeInit}`。

### 5. 分支与边界处理
- 分析关键条件分支、循环、递归、异常路径。
- 说明每条分支的触发条件、结果和风险。

### 6. 设计模式与架构决策
- 分析使用的设计模式（工厂、策略、观察者、模板方法等）。
- 对关键架构决策给出三维评估：好处、替代方案、风险。
- 说明决策背后的历史背景或业务约束（如有源码证据）。

### 7. 性能与资源分析
- 分析时间/空间复杂度、I/O 频率、缓存策略、资源复用。
- 标注可能的性能瓶颈和优化空间。

### 8. 潜在问题与改进建议
- 基于源码分析提出的潜在问题：如边界条件未覆盖、可能的内存泄漏、并发风险等。
- 每条问题说明严重程度、复现条件和改进建议。
- 区分"确认的问题"和"疑似问题（需进一步验证）"。

### 9. 文件职责表

| 文件 | 职责 | 关键类/函数 | 分析涉及章节 |
|------|------|-------------|-------------|

### 10. 代码引用索引

同模块文档的代码引用索引要求。

## 场景文档内容规范

### 重点关注

- 列出阅读本场景时最需要关注的入口、分支、状态或风险点。

### 1. 场景定义与边界

- 描述用户提出的场景、分析目标、包含范围和不包含范围。
- 明确哪些结论来自源码确认，哪些是基于调用关系的推断。

### 2. 入口、前置条件与触发方式

- 列出入口函数/API/事件/命令、前置配置、权限、输入参数和触发条件。
- 说明场景开始前系统需要处于什么状态。

### 3. 参与模块与职责

使用表格说明参与者：

| 模块/类/函数 | 角色 | 输入 | 输出 | 源码位置 |
|--------------|------|------|------|----------|

### 4. 调用时序图

- 必须使用 Mermaid sequenceDiagram，首行插入 `{_mermaidThemeInit}`。
- 使用 `Note over` 为每一步标注编号（如 `1. 接收请求`），步骤编号必须连续且每一道消息前都有对应 Note over。图后附步骤说明段落，段落编号与 Note over 编号一一对应。
- 覆盖主路径和关键失败/异步分支；复杂分支可拆成多个图。

### 5. 分步骤源码追踪

- 按时序图步骤逐步解释源码：调用者、被调用者、关键判断、输入输出、副作用。
- 每步至少引用一个源码位置；无法引用时说明原因。
- 不只复述函数名，要解释该步骤为什么存在、如何影响后续步骤。

### 6. 数据流、状态变化与副作用

- 跟踪核心数据对象从输入到输出的变化。
- 说明内存状态、持久化状态、缓存、消息、网络请求或文件系统副作用。

### 7. 分支、异常与异步处理

- 覆盖重要条件分支、异常路径、重试、回调、异步任务、事务/回滚或降级。
- 说明每条路径的触发条件、结果和风险。

### 8. 关键实现评估

- 对场景中最关键的 2-5 个实现点做三维评估：好处、替代方案、风险。
- 评估必须绑定具体源码位置。

### 9. 调试、验证与测试建议

- 给出可观察点：日志、断点、指标、状态检查、输入样例。
- 给出测试建议：主路径、失败路径、边界条件和回归点。
- 不要求运行源码；只提出静态分析后的验证建议。

### 10. 术语表

- 解释场景涉及的项目内术语、缩写、领域概念。
- 每个术语说明来源或对应源码位置。

### 11. 代码引用索引

同模块文档的代码引用索引要求。

## 章节质量门禁

子 agent 保存文档前必须检查：

- `hasStandardSections`：是否保留了对应文档类型的所有必需章节。
- `hasDetailedAnalysis`：核心章节是否包含源码证据、关键判断、数据/状态变化和三维评估。
- `hasDate`：是否通过 `_dateCmdFull` 获取并写入时间。
- `hasFocusSections`：是否有"重点关注"且不是空泛列表。
- `hasCodeRefs`：正文引用是否在"代码引用索引"集中列出。
- `mermaidChecked`：所有 Mermaid 图是否按规范插入主题并自查。
- `summarySynced`：新增、删除、改名或大幅修改文档后是否同步 `工程目录.md`。
